# Структура и нормализация базы LogParser 0.2

Основание: sql/schema.sql и src/db.c ветки feature/v0.2,
снимок 4fdec676012833c443c067e9dba40e6251caaf0c.
Это описание существующей модели, не предложение менять схему перед защитой.

## Сначала связи

sources хранит попытку загрузки файла. log_entries хранит события,
parse_errors — сохранённые ошибки разбора. В обеих дочерних таблицах
source_id ссылается на sources.id; связь один ко многим, удаление CASCADE.
Событие связано с попыткой, которая впервые его добавила. Повторный импорт
фиксирует новую попытку и счётчик дублей, но не создаёт повторное событие.
Поэтому удаление первой попытки удаляет и её события, даже если файл потом
импортировали повторно. Это текущая семантика, её нужно объяснить на защите.

## Функциональные зависимости

| Таблица | Ключи | Зависимости и оговорки |
|---|---|---|
| sources | PK id; UNIQUE(path, attempt) | Ключ определяет время, статус и счётчики одной попытки |
| log_entries | PK id; выражение уникального индекса | id определяет поля события и source_id |
| parse_errors | PK id | id определяет source_id, номер строки, исходный текст и дату |

Уникальность событий задаётся индексом по ts, host, coalesce(program,''),
coalesce(pid,-1), coalesce(level,'') и md5(message). Это практическая
дедупликация с хешем, а не доказательство абсолютной уникальности сообщений.

## Нормальные формы применительно к проекту

1НФ: поля содержат скалярные значения; списки событий вынесены в отдельные строки.
Текст сообщения остаётся единым значением по принятой модели.

2НФ: для первичных ключей id нет зависимости от части составного ключа.
Но формальная проверка требует учитывать все кандидатные ключи, а не только PK.

3НФ: нельзя без оговорок заявить её выполнение. Для известных уровней severity
вычисляется из level; оба значения хранятся ради фильтрации. Для нестандартных
уровней severity отсутствует. Это осознанное хранение производного признака.
Счётчики sources описывают результат попытки; после повторного импорта они
не равны простому количеству дочерних событий этой попытки.

4НФ: проверяет независимые многозначные зависимости. Модель не хранит
несколько независимых списков в одной строке; отдельного доказательства
4НФ в проекте нет.

5НФ: проверяет зависимости соединения и возможность дальнейшего разложения
без потерь. Соответствие 5НФ для проекта не доказано; заявлять его нельзя.
НФ Бойса—Кодда также требует отдельного анализа всех детерминантов.

## Точка входа и работа db.c

main.c передаёт параметры подключения в db_connect. libpq создаёт PGconn.
Далее обработчик команды вызывает db_search, db_trace или функции статистики;
результат PGresult передаётся в модуль отображения. db_search строит SQL из
фиксированных фрагментов и параметров, db_trace выбирает цепочку по trace_id.
Импорт использует db_source_start, db_copy_begin/row/end, db_stage_commit,
db_insert_parse_error и db_source_finish. Транзакцией управляет importer.c.

До патча атомарности статус ok обновляется после COMMIT и ошибка обновления
не проверяется. После патча Александра статус ok входит в транзакцию данных.
При обрыве соединения фиксация статуса failed всё равно не гарантирована.

## Производительность

Сначала выполнить sql/check_indexes.sql на тестовой базе с характерным объёмом.
Записать EXPLAIN (ANALYZE, BUFFERS), размер данных, версии и условия запуска.
Индекс нельзя добавлять только ради количества коммитов: сравнить планы и
время на одинаковых данных до/после. Если улучшения нет, оставить схему.
