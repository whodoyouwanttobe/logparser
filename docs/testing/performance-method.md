# Воспроизводимый замер обработки

```sh
make
python3 scripts/benchmark_parse.py --output docs/testing/parse-baseline.csv
```

Нагрузки: 10 000, 100 000, 1 000 000 строк; один прогрев и пять повторов.
Скрипт сохраняет каждый замер, медиану, число строк и байт, SHA и платформу.
CSV не перезаписывается. Во время замера не запускать сборку и другие нагрузки.

Измеряется CLI parse: запуск процесса, чтение файла, разбор и форматирование
вывода с перенаправлением в /dev/null. PostgreSQL и import не участвуют.
Это не тот же эксперимент, что изолированный вызов parse_line; сравнивать
цифры этих двух методик напрямую нельзя. Код parse возвращает успех даже
при плохих строках, поэтому корректность формата проверяется отдельно.

## Окружение фактического baseline

- CPU: 11th Gen Intel Core i7-11370H @ 3.30 GHz, 4 ядра / 8 потоков.
- ОЗУ: 23,69 ГиБ физической памяти.
- ОС: Windows 11 Pro, версия 10.0.26200; исполняемый файл собран в MSYS2 3.6.12.
- Компилятор: GCC 16.2.0; GNU Make 4.4.1; libpq из PostgreSQL 18.7.
- Флаги: `-std=c11 -O2 -g -Wall -Wextra -Wpedantic -Wshadow -Wstrict-prototypes`.
- SHA: `4fdec676012833c443c067e9dba40e6251caaf0c`.
- Статус дерева: `src/`, `Makefile` и `tests/` соответствовали SHA; добавлялись только
  файлы методики и замера. Поэтому SHA описывает измеряемый код парсера и CLI.
- Запуск на этом ПК: `python scripts/benchmark_parse.py --binary ./logparser.exe --output docs/testing/parse-baseline.csv`.
  В Linux достаточно команды из начала документа, без `--binary`.

В отчёт добавить CPU, ОЗУ, ОС, компилятор и флаги, версии, SHA и статус рабочего
дерева. Если дерево изменено, SHA не полностью описывает измеряемый код:
сохранить diff или делать итоговый запуск после коммита.
