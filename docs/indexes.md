# Индексы LogParser: зачем каждый оставлен

Редакция 27.10.2026. Проверены реальные запросы src/db.c, а не только названия полей. Статистика выполнения на машинах команды не получена. Поэтому здесь нет утверждения, что удалённые индексы никогда не используются, и нет обещанных процентов ускорения.

## Простое объяснение

Индекс похож на указатель в книге: вместо чтения всех страниц можно перейти к подходящим местам. Но указатель занимает место и должен обновляться при добавлении записей.

В PostgreSQL индексы применяют для поиска по условиям, соединения таблиц, выдачи строк в определённом порядке. Уникальные индексы также запрещают повторяющиеся значения. Не нужно индексировать «весь объёмный запрос»: выбирают поля и их порядок под конкретные условия и сортировку. Важно, какая часть таблицы нужна запросу, а не только как часто его вызывают.

## Что изменено

Вместо шести прежних поисковых индексов оставлены два B-tree под основные команды. Индексы первичных ключей, уникальности событий/попыток и связей source_id сохранены отдельно.

| Прежний индекс | Решение | Обоснование и цена решения |
|---|---|---|
| log_entries_ts_brin | Удалён; вместо него (ts,id) | BRIN рассчитан на связь значений с физическим порядком хранения. Файлы можно загружать не по времени. B-tree соответствует реальному ORDER BY ts,id LIMIT |
| log_entries_sev_ts | Удалён из базового набора | severity<=N бывает широким фильтром; индекс не гарантирует выдачу всех уровней сразу в общем порядке времени. При редких ошибках он может быть полезен, это проверяется отдельно |
| log_entries_level | Удалён из базового набора | Поиск точного уровня есть, но необходимость отдельного индекса без данных о распределении не доказана. Низкое число уровней само по себе не доказывает бесполезность |
| log_entries_prog_ts | Удалён из базового набора | Для program=... индекс подходит, но частота такого поиска и выигрыш неизвестны. При частом поиске редкой программы можно обоснованно вернуть |
| log_entries_trace | Заменён на (trace_id,ts,id) | Команда trace выбирает одну операцию и сортирует по времени, затем ID; новый индекс включает весь порядок |
| log_entries_msg_trgm | Удалён из базового набора | GIN/pg_trgm действительно может помогать ILIKE '%текст%'. Сейчас сокращаем расходы на импорт и хранение; текстовый поиск на больших наборах может стать медленнее |

Поиск по уровню, программе и тексту НЕ удалён. Меняется способ, которым PostgreSQL может выполнить запрос. При необходимости он просмотрит строки и проверит условия.

Новая схема не требует pg_trgm.

## Какие индексы остаются

| Индекс | Конкретное назначение |
|---|---|
| sources_pkey, log_entries_pkey, parse_errors_pkey | PRIMARY KEY автоматически создаёт уникальные B-tree. Обеспечивают уникальность ID; sources по id обновляется и выводится в истории |
| sources_path_attempt_key: UNIQUE(path,attempt) | Запрещает одинаковые номера попыток одного пути. Также соответствует WHERE path=$1 при поиске MAX(attempt) |
| log_entries_uniq | Запрещает повторные события; используется при INSERT ... ON CONFLICT DO NOTHING |
| log_entries_ts_id: (ts,id) | db_search выбирает последние N строк: ORDER BY ts DESC,id DESC LIMIT N. B-tree допускает обратный просмотр; после отбора маленький набор выводится по возрастанию |
| log_entries_trace_ts_id: (trace_id,ts,id), только trace_id IS NOT NULL | db_trace и search -t выбирают конкретную операцию; записи без trace не занимают место в этом индексе |
| log_entries_source, parse_errors_source | Помогают найти дочерние строки по source_id при удалении попытки. Для правильности CASCADE индекс не обязателен, но FK на дочерней стороне не создаёт его автоматически |

Уникальный индекс событий начинается с ts, но дальше содержит host/program и другие поля. Он не даёт тот же порядок (ts,id), что отдельный индекс для списка последних событий.

При выборке всех строк ради count или GROUP BY PostgreSQL всё равно должен обработать значительную часть данных. Индекс trace не объявляется универсальным ускорителем отчёта по всем операциям.

## Почему именно (path,attempt)

path - путь файла, attempt - номер его загрузки. Разрешено:

| path | attempt |
|---|---|
| sample.log | 1 |
| sample.log | 2 |
| app.log | 1 |

Вторая строка `(sample.log,2)` запрещена. Только UNIQUE(path) запретил бы повторную загрузку файла. Только UNIQUE(attempt) запретил бы первую попытку другого файла. PRIMARY KEY(id) не запрещает одинаковые пары при разных ID.

Главная причина индекса - правило целостности, а не обещание быстрого поиска. Порядок path первым также соответствует запросу регистрации:

```sql
SELECT coalesce(max(attempt),0)+1 FROM sources WHERE path=$1;
```

Путь не является отпечатком содержимого файла: разные записи пути могут считаться разными источниками. Номера относятся к сохранённой истории; после удаления последних попыток номер может использоваться снова. Для регистрации MAX+1 также нужна синхронизация: подготовленный db_source_start использует короткую блокирующую транзакцию. Уникальность сама по себе только отклонила бы конфликтующую вставку.

## Как доказать пользу, а не предположить её

Использовать копию БД с характерным объёмом и распределением данных. Сначала ANALYZE, затем EXPLAIN (ANALYZE, BUFFERS). Не отключать Seq Scan ради красивого результата. На 34 строках последовательное чтение часто разумнее любого индекса.

Готовые запросы: sql/check_indexes.sql. Для сравнения до/после запускать их на одинаковом наборе, записывать планы, время и buffers. Повторить несколько раз и учитывать прогрев. Показатели idx_scan смотреть после обычной работы: ноль после перезапуска статистики не доказывает ненужность индекса; для UNIQUE его защитная функция важна независимо от этого счётчика.

Синтетический тест показывает только поведение на синтетических данных. Реальную частоту запросов пользователей он не устанавливает.

## Ответ преподавателю в нескольких фразах

Мы разделили индексы для целостности и для ускорения. Уникальность файла и номера попытки нужна, чтобы не появлялись две одинаковые попытки одного файла. Для поиска оставили индексы по времени с ID и по trace_id со временем и ID: они соответствуют командам списка и просмотра операции. Остальные поисковые индексы убрали из минимальной схемы, а не объявили всегда бесполезными. Их возвращение будем обосновывать планом и измерением реального запроса.
