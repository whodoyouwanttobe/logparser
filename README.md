# logparser

**logparser** — консольная утилита для загрузки, хранения, поиска и анализа системных логов.
Она загружает один или несколько файлов логов в PostgreSQL и позволяет искать записи, собирать цепочки операций по `trace_id` и смотреть статистику.

Сценарий использования такой: принести логи с сервера (на флешке, архивом), запустить PostgreSQL одной командой, загрузить файлы, разобраться, что произошло, и очистить базу перед следующим набором логов.

## Быстрый старт через Docker

Нужен только **Docker Desktop** (Windows/macOS) или **Docker Engine + Compose** (Linux). Компилятор, библиотеки и PostgreSQL ставить не нужно, всё запускается в контейнерах.

```bash
git clone https://github.com/whodoyouwanttobe/logparser.git
cd logparser

# 1. Запустить PostgreSQL. Схема БД создаётся автоматически, init вызывать не нужно
docker compose up -d

# 2. Положить свои логи в папку logs/ (например, скопировать с флешки)
cp /media/usb/syslog logs/

# 3. Работать с утилитой. ./lp — обёртка над `docker compose run --rm logparser`
./lp import /logs/syslog                # свои логи из папки logs/
./lp import samples/sample.log samples/app.log   # или примеры из репозитория
./lp search -l error
./lp trace a1b2c3
./lp stats

# 4. Закончить работу
./lp clear              # удалить загруженные данные (структура БД остаётся)
docker compose down     # остановить PostgreSQL (данные в томе сохраняются)
docker compose down -v  # остановить и удалить все данные
```

**Windows.** В PowerShell или cmd используйте `lp.cmd` вместо `./lp`, например `.\lp.cmd import /logs/syslog`. В Git Bash работает `./lp`.

Первый запуск `./lp` собирает образ утилиты, это занимает около минуты. Последующие запуски мгновенные. После изменения кода пересоберите образ командой `docker compose build`.

Если порт 5432 уже занят (на компьютере есть свой PostgreSQL), скопируйте `.env.example` в `.env` и поменяйте `PGPORT=5433`.

## Локальная сборка без Docker

Подходит для Linux или WSL (Ubuntu внутри Windows: `wsl --install -d Ubuntu`).

```bash
sudo apt install build-essential libpq-dev clang-format   # компилятор и libpq
make            # собрать ./logparser
make test       # unit-тесты парсера (БД не нужна)
```

PostgreSQL можно запустить так же через `docker compose up -d`, либо использовать установленный локально:

```bash
# только для локального PostgreSQL:
sudo -u postgres createuser -s $USER && createdb logs
export PGDATABASE=logs
./logparser init        # создать схему
```

С PostgreSQL из Docker подойдут настройки из `.env.example`:

```bash
cp .env.example .env
set -a; . ./.env; set +a      # загрузить переменные PG* в текущий терминал
./logparser import samples/sample.log
```

## Настройки подключения

Подключение к PostgreSQL выполняет библиотека **libpq**. Если не передать параметры явно, она читает стандартные переменные окружения:

| Переменная | Что задаёт | По умолчанию в `.env.example` |
|---|---|---|
| `PGHOST` | адрес сервера | `localhost` (внутри Docker — `db`) |
| `PGPORT` | порт | `5432` |
| `PGDATABASE` | имя базы | `logs` |
| `PGUSER` | пользователь | `logparser` |
| `PGPASSWORD` | пароль | `logparser` |
| `PGTZ` | часовой пояс для времени без зоны (`Oct 10 12:34:56`) | `Asia/Novosibirsk` |

Так можно выбрать нужный сервер, если их запущено несколько, и для этого не нужно менять код. Вместо переменных можно передать строку подключения:

```bash
./logparser -d "host=192.168.1.10 port=5433 dbname=logs user=logparser password=secret" stats
```

Команды `init` и `clear` выводят, к какому серверу подключились: `подключено: localhost:5432/logs`.

## Формат входных логов

Одна строка — одна запись:

```
[<PRI>]ВРЕМЯ ХОСТ ПРОГРАММА[PID]: СООБЩЕНИЕ
```

| Часть | Варианты | Обязательно |
|---|---|---|
| `ВРЕМЯ` | `Oct 10 12:34:56` (syslog, RFC 3164) или ISO 8601 `2026-10-10T12:34:56.123+07:00` (rsyslog, `journalctl -o short-iso`) | да |
| `ХОСТ` | имя хоста | да |
| `ПРОГРАММА[PID]:` | `sshd[2301]:`, `kernel:` | нет |
| уровень | `<PRI>` в начале строки, или в начале сообщения `[ERROR]` / `<warn>` / `FATAL:` / `error:`, или поле `level=warning` | нет |
| `trace_id` | поле `trace_id=a1b2c3` (также `traceId=`, `trace-id=`, `trace=`) | нет |

**Уровень не угадывается по словам в тексте.** Сообщение `Connection failed` без разметки уровня сохраняется без уровня («-»), а не как ошибка. Нестандартные уровни (`FATAL`, `TRACE`, `AUDIT`) сохраняются как есть, в нижнем регистре, и не заменяются на `unknown`. Подробнее: [docs/database.md](docs/database.md#уровни-level--severity).

Строки, которые не подходят под формат, не теряются: они попадают в таблицу `parse_errors` вместе с номером строки.

Примеры: [`samples/sample.log`](samples/sample.log) (системный syslog) и [`samples/app.log`](samples/app.log) (лог приложения с `trace_id`).

## Команды

```
logparser [-d CONNINFO] <команда> [опции]
```

| Команда | Что делает |
|---|---|
| `init [schema.sql]` | создать схему БД (в Docker Compose делается автоматически) |
| `import FILE...` | загрузить один или несколько файлов; `-` читает stdin. Повторный импорт того же файла не создаёт дубликатов |
| `parse [-n N] FILE` | разобрать файл без БД и показать поля (проверка формата) |
| `search [фильтры]` | найти записи |
| `trace ID` | все записи одной операции по порядку, со смещением от начала и общей длительностью |
| `stats [-s TIME] [--hours N] [--top N]` | сводка, распределение по уровням, топ-N программ и хостов по ошибкам, топ-N самых долгих операций, активность по часам |
| `sources [-n N]` | история попыток импорта: файл, номер попытки, статус, сколько новых строк, дублей и ошибок |
| `clear [-y]` | удалить все загруженные данные с подтверждением `[y/N]`. Структура БД сохраняется |

Фильтры `search`:

| Опция | Пример | Смысл |
|---|---|---|
| `-l, --level` | `-l warning` | уровень не ниже указанного (по коду 0..7) |
| `-L, --level-is` | `-L fatal`, `-L -` | точно этот уровень, в том числе нестандартный; `-` — записи без уровня |
| `-p, --program` | `-p sshd` | программа |
| `-H, --host` | `-H srv01` | хост |
| `-t, --trace` | `-t a1b2c3` | одна операция |
| `-s, --since` / `-u, --until` | `-s 2h`, `-s "2026-10-10 08:00"` | период: относительный (`30m`, `2h`, `7d`) или абсолютный |
| `-g, --grep` | `-g "failed password"` | подстрока в сообщении |
| `-n, --limit` | `-n 100` | сколько последних записей показать |
| `-f, --format` | `-f csv > out.csv` | `table` или `csv` |

Примеры:

```bash
./logparser import samples/sample.log samples/app.log
./logparser search -l error -s 1h
./logparser search -p sshd -g "failed password" -f csv > ssh.csv
./logparser trace f7a8b9
./logparser stats --top 5
journalctl -o short-iso --since today | ./logparser import -
```

Полный список опций выводит `./logparser --help`.

## Архитектура

Это одно приложение с командами. Загрузка и анализ живут в одной утилите, потому что она рассчитана на локальную работу с принесёнными логами, а не на постоянный сбор с серверов.

```
main.c  ──►  ui.c                    фронтенд: команды, вывод, цвета
   │
   └──►  importer.c  ──►  parser.c   бэкенд: чтение файлов и разбор строк
              │
              └──►  db.c  ──►  PostgreSQL   БД: схема в sql/schema.sql
```

| Модуль | Ответственность |
|---|---|
| `parser.c` | разбор одной строки в `log_entry`: время, хост, программа, PID, явный уровень, trace_id. Без зависимостей |
| `importer.c` | чтение файла или stdin, учёт попытки, подсчёт новых строк, дублей и нестандартных уровней |
| `db.c` | всё, что касается libpq: подключение, COPY, защита от дублей, параметризованные запросы |
| `ui.c` | таблицы, цвета по уровням (цвета есть только здесь, в БД их нет), гистограммы, CSV |
| `main.c` | разбор аргументов и запуск команд |

Подробнее: [docs/database.md](docs/database.md) — схема БД и ER-диаграмма, [CONTRIBUTING.md](CONTRIBUTING.md) — код-стайл и Git Flow.
